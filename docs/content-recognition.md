# 程序内容识别备忘录

记录日期：2026-10-19。

程序内容识别是 WorkState 中没有完美答案的问题。窗口标题是有限、非标准化的信息源；规则应保持有限、可解释，在有明确依据时细分，识别不了时保留程序级统计。

## 浏览器标题方案的局限

当前方案只对配置名单中的浏览器进行处理：先清理已知的浏览器名称后缀，再对网页标题匹配给定的网站名关键词；不区分大小写，较长关键词优先。它只能识别名单覆盖的部分网站，不能由标题可靠推断真实网站。

其他网站的文章、搜索结果或聊天话题也可能包含目标网站名。例如，豆包页面的讨论标题包含“Google”时，仍可能被分到 Google。长度优先只解决重叠关键词的选择，不代表网站归属更准确。

清理浏览器后缀属于应当完成的基本处理，与上述信息不足是两回事。例如：

```text
项目数据保存方式分析 - 豆包 - Google Chrome
                         ↓ 去掉浏览器后缀
项目数据保存方式分析 - 豆包
```

修正前，浏览器分支未执行后缀清理，`Google` 会因为长于“豆包”而从 `Google Chrome` 中先被命中。这是实现缺陷。修正后，仅剔除标题末尾明确的浏览器名称，不随意丢弃最后一个标题片段，以免把真正的网站名删除。自定义浏览器只能识别与其进程名相同的后缀，其他品牌格式仍需适配。

## UIA 获取网址的可行性

Windows UI Automation（UIA）可以读取浏览器的地址栏，部分浏览器还会在网页文档节点提供完整 URL。使用 URL 解析后的主机名做网站归属，可以显著减少标题话题、浏览器品牌等带来的误识别。

本机临时测试已在 Chrome、Edge 的多个真实网站读取到地址，包括豆包重定向后的聊天页。Chrome 地址栏可能省略协议和 `www`，网页文档节点可以补充完整 URL；本机 Edge 的地址栏也能提供完整 URL。读取结果会反映重定向后的实际地址，而非固定保留最初请求的网址。

这些是正常窗口下的有限样本，不能视为所有浏览器、版本和运行状态的可靠性保证。网页加载、登录要求和访问限制也要与“UIA 能否读取地址”分开判断。

## 接入所需的变化

目前活动记录只保存程序和窗口标题。标题不能可靠还原旧记录当时的网址，因此 UIA 不能仅作为报表阶段的新解析函数接入。

- 需要在浏览器处于活动状态时，额外采集并保存网站信息，关联到对应的分钟活动记录。若只为网站统计，优先保存主机名；完整 URL 是否保留应另行决定。
- 需要扩展数据库结构。可增加一张网站信息表关联现有活动记录；也可以评估增加字段。新增表不是 UIA 的技术硬性要求，但持久化结构必须能够容纳网站信息。
- 需要联动修改记录采集、数据库读写、报表聚合，以及涉及该信息的导入导出；既有历史数据只能继续按标题回退。
- 依赖系统和浏览器对 UIA 的支持；版本、语言、全屏、地址栏编辑、多窗口等状态均需验证。采集前后还应核对前台窗口，防止窗口切换时把网址关联到错误的分钟记录。
- 读取应设置超时并隔离阻塞，失败时保留原始活动记录。地址栏正在编辑时的文本不能直接当作已打开网页的网址。

## 当前决定

先修正标题解析中的浏览器后缀缺陷，保留有限的关键词规则。UIA 作为后续增强方向，暂不接入正式采集链路，不变更现有数据库、记录格式或 CSV 格式。
